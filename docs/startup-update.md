# 0.7.3 — confirmed settings-reopen fix

The user's 0.7.2 startup.log showed normal UAC handshake completion followed by ui-initializing then generic error 574. A read-only --config-probe on the user's original settings reproduced `regex_error(error_stack): There was insufficient memory to determine whether the regular expression could match the specified character sequence.` The saved settings were valid (706 bytes); Config::load validated them outside Config::parse's catch. The prior empty-profile smoke test therefore missed the failure. No settings deletion/reset is needed.

The full-object recursive regex and per-field regex searches are replaced with an iterative, bounded parser for this existing flat integer/boolean schema. Inputs >=64 KiB, malformed tokens, trailing content, duplicate keys and unsupported nested/string values are rejected. Existing migration/default/clamping and backups remain. Regression coverage includes the complete pre-fix settings fixture, save/load/save/reopen (including reminder preferences), malformed JSON, and 60,000 whitespace characters. --config-probe remains read-only. Standard-exception diagnostics now include the exception type (not its potentially private message), with UI construction/config-loaded stage markers.

## 0.7.2 — resilient startup and worker exception diagnostics

0.7.3 verified: read-only --config-probe now loads the original user's unchanged settings with horizontalPercent=88 and lastPage=4. SHA256 before/after confirms the original settings were not modified. CTest passes 1/1 including complete-settings save/reopen, malformed input and large whitespace cases. Full production initialization using a copied settings file in a disposable profile reached ui-config-loaded, full-services-ui-ready and google-worker-ready, stayed active 30 seconds and exited 0. Graphical previews passed with a freshly timestamped verification report; installer rebuilt and the previously reported startup-x64/Release executable updated to 0.7.3.0, preserving a 0.7.2 executable backup. Real UAC approval was not exercised in the tool environment; the user's own log already confirms the 0.7.2 handshake succeeded before the reproduced config-load failure.

The reported 1346 error was the linked-token DuplicateTokenEx call. That path is removed: an already elevated entry now keeps its current process and displays a warning that Explorer-to-island drag/drop is restricted by Windows integrity levels. Normal entry still requests the elevated monitoring host, but denied/cancelled UAC, event/host startup errors and handshake timeout no longer prevent the normal-user UI from opening. This deliberately prioritizes availability over mandatory elevation if elevation cannot be obtained. The legacy --desktop-ui argument no longer requires an admin-host mutex.

The separate user Event Viewer report (ucrtbase.dll, 0xc0000409) establishes fail-fast termination, not its exact cause. Google worker apartment/JsonObject initialization was outside its local catch blocks and only runs in production; the old isolated UI smoke test disabled that worker. All service entry points now contain C++/WinRT and standard exceptions and log stage + numeric error, without clipboard/calendar/token contents. Google startup failure updates its UI status rather than killing the application. Its apartment lifetime now outlives its WinRT local objects. UI-entry exceptions are reported; a last-resort terminate handler reports and logs unexpected C++ termination. These are not a guarantee against memory corruption or Windows fail-fast operations, which require a crash dump to diagnose.

Diagnostics are bounded to 256 KiB (reset on the next append exceeding the bound) at %LOCALAPPDATA%/NativeIsland/startup.log. Version resources now identify the executable as 0.7.2.0 instead of 0.0.0.0. Settings/reminders/vault paths and installer AppId remain unchanged.

--runtime-smoke-test exercises the production initialization with ALL workers enabled for 30 seconds and bypasses UAC. Run only with a disposable LOCALAPPDATA environment, because it intentionally uses real persistence paths and startup behavior. It uses the verification mutex so it does not interfere with an existing normal instance. This test is not a substitute for accepting real UAC in the interactive user's session.

## Historical 0.7.1 implementation and verification (superseded)

0.7.2 verification: clean Release build succeeded; executable resource reports 0.7.2.0. CTest passed 1/1 (including injected standard and WinRT worker exceptions). The restricted tool sandbox initially denied the ready-event test; the same test passed outside that filesystem sandbox, without a real administrator token. A properly awaited --runtime-smoke-test with disposable LOCALAPPDATA reached full-services-ui-ready and google-worker-ready, ran 30 seconds and exited 0. The full graphical --render-previews regression exited 0 (settings dropdowns, owned popup/dialog ordering, reminder CRUD, six themes/pages, animation, clipboard/image fixtures). Installer built successfully. Actual interactive UAC acceptance and an already-elevated process remain unverified here; the original user's fail-fast call stack was not available and its exact cause is not claimed as proven.

Previously normal startup elevated a host, then asked Explorer's desktop IShellDispatch2 to relaunch the UI. Both a failed shell COM call and a missing UI HWND after 20 seconds produced the same misleading Explorer error. This path is removed.

Normal double-click now asks UAC approval for an admin monitoring host but keeps the ORIGINAL normal-user process as the UI. The host validates the original PID's executable image, same Windows session and liveness, then acknowledges a random GUID-named event and waits for that process to exit. Event access is limited to the original user, Administrators and SYSTEM. There is no privileged command interface. A startup mutex prevents overlapping launches; the existing UI single-instance mutex remains.

Explicit "Run as administrator" uses the current user's linked unelevated token via CreateProcessWithTokenW and a matching user environment. If no normal linked token is available, the app reports a Windows code and advises a normal double-click rather than silently running its drag/drop UI at high integrity. Running under another administrator account can use that administrator's data profile on this explicit path; prefer normal double-click, which retains the original user's profile even when UAC uses another administrator's credentials.

Existing settings, reminder data, Google credentials and installation AppId paths are unchanged. No user data is deleted by this fix.

Implementation references: [CreateProcessWithTokenW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createprocesswithtokenw), [TOKEN_LINKED_TOKEN](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-token_linked_token).

Verification covers strict host arguments and invalid PIDs/events, event ACL creation/signaling/collision rejection and executable/session/liveness checks using a short-lived same-image child. --startup-handshake-test is an isolated verification role: it exports its random ready-event name and PID to out/startup-handshake.txt, waits up to 60 seconds for an explicitly launched admin host, then renders the UI in its ORIGINAL normal-user process for 6 seconds. It does not load/save user reminders or Google tokens. Ordinary --render-previews and --smoke-test remain isolated verification roles. UAC dialog acceptance and explicit elevated linked-token launching must be confirmed in the user's interactive session; they are not simulated by these tests.

The clean Release build and extended CTest suite passed (1/1). The test event also matches its creator's integrity label, permitting the same-user restricted/low-integrity test process to signal its own event without broadening the user ACL. An attempted admin-host integration run in the tool executor returned ERROR_ELEVATION_REQUIRED (740): sandbox escalation did not grant a real elevated Windows token. The handshake probe consequently timed out, so full admin-host/UAC integration is NOT reported as passed. No existing user application was killed or installation upgraded during testing.
